Executor tools send the request the spec describes.

Executor turns OpenAPI specs into tools an agent can call. I checked what those tools actually send. Two things were wrong: the query string was rewritten on the way out, and some tools could never work.

Offline sample of 134 apps and 68,090 generated inputs, with both changes applied together. The two changes were not measured separately. The 157 and the 0 are import-level counts, which do not depend on the query change. No live provider was called.

open: PR #2590

Send the query as built

The runtime read each query into parameters and encoded it again as a form. Commas, slashes and colons were escaped and %20 became +. Now the URL goes out as built. Two scenarios and 6 files.

01

How a tool call becomes a request

The builder serializes each parameter by its OpenAPI style. Then the runtime sends the request through the Effect HTTP client. One step in that path rewrote the query.

02

Cause and fix of the query change

HttpClientRequest.fromWeb reads a URL's query into a list of parameters, and the client appends them again with form encoding. That escapes commas, slashes and colons, and turns %20 into +. The spec says a form list with explode: false is tags=red,blue.

asSent keeps fromWeb(request) for the method, headers, body and signal, clears the parsed parameters, and sets the original URL again without its fragment. A bare trailing ? survives. The OpenAPI builder escapes only what a URI query cannot hold. It refuses a reserved value containing #, which would cut the query short.

Three controls that make the tests mean something

  • Real upstream code with only the new scenarios added: both query scenarios fail. The first fails on tags=red%2Cblue where tags=red,blue is expected.
  • Earlier fetch code that dropped the bare ?: the ctx.fetch scenario fails on that case.
  • Keepalive: the upstream server cannot observe the flag, so the keepalive case shows that the request and its body arrive with the query as written. It does not show that the flag was forwarded.

04

Why the check refuses so little

An early draft refused every operation that declares a path parameter its path does not hold. Measuring the 36 operations that rule hit in 9 stored specs showed that 25 of them sent a correct request, because the extra parameter is simply ignored. So the final check refuses only what can never work, and describes the rest in the tool description.

An independent review also caught that the regex-group rule refused any literal parenthesis, so /items(archived)/{id} with an extra parameter was wrongly refused. The rule now needs a backslash or a group such as ([0-9]+), and the scenario covers it.

07

How the numbers were measured

  • For each operation of each sampled spec, an input is generated from the tool's own schema in three profiles (plain, required fields only, reserved characters). The request is captured by a fetch that never reaches a network.
  • The captured request is compared with the OpenAPI serialization rules by a separate checker, not with the old behaviour. Results are match, encoding, unsure or wrong.
  • The same sweep runs on upstream v2 and on the tree with both changes. Pair counts are per operation and profile. The page's headline counts operations.
  • A regression gate stores one verdict per operation for 18 apps (4,792 operations) and fails on anything worse.
  • Both changes were applied together for the sweep. They were not measured separately.
08

Limits

  • An undeclared placeholder after ? (/find?limit={limit} with no limit declared) is not diagnosed and is sent as limit=%7Blimit%7D. A query may also hold literal braces.
  • /jobs/:jobId.json declaring jobId, and /jobs/:id declaring jobId, are kept and send the colon segment as written.
  • A kept unused path parameter stays required in the tool input, so an agent must give it a value that is then dropped.
  • With allowReserved, a literal %2F is still sent as %252F. The cause is in swagger-client and it predates this work.
  • The keepalive scenario shows the request and body arrive, not that the flag is forwarded, because the upstream server cannot observe it. No live provider was called. Nested serialization and binary or multipart bodies are not covered.
  • pr:check cannot run as a whole because v2 and main share no history. Its parts were run for the query change, and for an earlier revision of the import change. The apps-version step was not run.
09

Reproduce

You need Git, Bun, Docker (for the self-host scenarios) and Node 22 or later. PORTFOLIO is the folder that holds this page's README.md and patches/. EXECUTOR is a fresh clone of UsefulSoftwareCo/executor.

1. Get Executor at the base commit and apply both patches

export PORTFOLIO="$PWD"
export EXECUTOR="$HOME/executor"
git clone https://github.com/UsefulSoftwareCo/executor "$EXECUTOR"
cd "$EXECUTOR"
git checkout 45e39ee12
git am --3way "$PORTFOLIO/patches/pr2-query-as-sent.patch" "$PORTFOLIO/patches/pr1-import-diagnostics.patch"

Both patches are against v2 at 45e39ee12. git am needs user.name and user.email set. Applying only one patch works too.

2. Run the scenarios, from $EXECUTOR

bun install
bun run e2e:self-host --test-name "An app's fetch sends its query to the upstream exactly as written"
bun run e2e:self-host --test-name "Imported OpenAPI query parameters reach the upstream as OpenAPI serializes each style"
bun run e2e:self-host --test-name "OpenAPI import reports a misnamed path parameter"

To see a control fail, check out 45e39ee12 again, copy only the three files from $PORTFOLIO/tests/ into e2e/tests/, add their entries to e2e/test-plan.ts from the patches, and run the same commands.

3. The page's import rules, from $PORTFOLIO

cd "$PORTFOLIO"
node --test tests/rules-port.test.mjs

The measurement harness and the offline demo are in reproduce/. The public spec files they read are not bundled. reproduce/README.md says where to put them.
